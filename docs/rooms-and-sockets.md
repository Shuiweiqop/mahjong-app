# Rooms, sockets, and the clock

Read this before touching `server/server.js` or `server/rooms.js` — join/rejoin, spectators,
host transfer, and the countdown interact in ways you can't infer from either file alone.

## Two membership lists, not one

A room has **`members`** (in the game, in `state.players`, occupy `maxPlayers`) and
**`spectators`** (joined mid-game, no role, don't occupy a slot). `joinRoom` decides which you
become, and the test is `room.state != null` — **not** the phase.

`createInitialState` already returns a state whose phase is `'lobby'`, so "has the game started"
and "is the phase past lobby" are different questions. Using phase here would silently drop
lobby-stage joiners into the spectator list.

These two lists are separate data from `state.players`, and drift between them is the source of
the nastiest bugs in this layer — a member removed from one but not the other becomes a ghost
player the phase machine waits on forever. `leaveRoom` calls the module's `eliminatePlayer` for
exactly this reason: merely marking someone absent means the game can never end if the only wolf
quits.

## Three broadcast surfaces, three different views

`broadcastState` fans out to three audiences with three payloads. Adding a fourth path, or
reusing the wrong one, is how information leaks:

| Audience | Payload | Built by |
|---|---|---|
| Members | per-player view + room-level spectator info | `playerViewFor` → module's `serializeStateFor(state, m.id)` |
| Spectators | one shared public view | `roomsMgr.spectatorViewFor` |
| Whole room | non-hidden increments (`stroke`, `chat`, `guessed`, `reveal`, `game_over`) | the `extraEvents` loop |

**The spectator view is generated by calling `serializeStateFor` with a player id that doesn't
exist** (`'__spectator__'` in `rooms.js`). It works only because both modules build their view by
allow-list, so an unrecognized id naturally matches no role branch and receives pure public data.
This is a *convention every game module must uphold*, not something the platform enforces —
a module that assigns a default role to unknown ids, or attaches `roles` unconditionally, hands
every secret to anyone who opens a second tab and spectates.

`server/games/contract.test.js` pins this down: it calls each module's `serializeStateFor` with an
unknown id and fails if `roles` or `myRole` comes back. Run `npm test` in `server/` after touching
any `serializeStateFor`.

Host-enabled **god view** (`room.spectatorGodView`, off by default) is the one sanctioned way
spectators see roles. It defaults off deliberately: on by default, any player could open a second
tab, spectate, and see the whole table.

### The dead chat channel is a fourth hiding surface

`chat` events with `channel: 'dead'` go only to eliminated players plus spectators
(`deadChannelSockets`), because living players must not read what the dead say. An event with no
channel, or `'alive'`, is public to the room. If you add a chat-like event, decide which of these
it is — routing a dead-channel message through `io.to(room.code)` spoils the game for everyone
and looks completely normal in the diff.

## The clock: `deadline` is an absolute timestamp

Each game stores `state.deadline` as `Date.now() + n`. That means **wall-clock time keeps running
even when nobody is connected** — without intervention, a room everyone disconnects from for two
minutes comes back with its phase already expired.

The fix is split across two layers on purpose, and the split is the part to understand:

- **The transport layer decides *whether* to stop the clock.** Only `server.js` knows whether any
  socket is still attached (`roomIsEmpty`), and it calls `pauseRoomClock` / `resumeRoomClock`.
- **The game module decides *how*.** `pauseClock(state)` stashes the remaining span in
  `pausedRemainMs` and nulls `deadline`; `resumeClock(state)` sets a fresh
  `deadline = now() + pausedRemainMs`.

"Is anyone watching?" and "can anyone still act?" are **not the same question** — a room of all-dead
players plus spectators still needs its clock running. That's why the module never decides this
itself, and why `removePlayer` / `eliminatePlayer` deliberately don't touch `deadline`.

If you add a game with timed phases, implement both `pauseClock` and `resumeClock`. The contract
test asserts they exist as a pair and that pause actually clears `deadline` — half an
implementation turns it red.

## Time advances server-side only

`ensureTimer` ticks once a second and calls `applyAction(state, { type: 'tick' }, null)`. Note the
`null` player id: a tick has no actor. Never accept a client-sent `tick`, and never trust a
client-reported elapsed time — a player controls their own socket and would simply skip the night.

Werewolf's `hurryDay` shortens `deadline` once everyone has voted, and it only ever moves the
deadline **earlier** (`if (hurryUntil < s.deadline)`). Keep that one-directional: letting a late
vote push the deadline back gives the last voter unlimited stalling power.

## Rejoin vs. spectate vs. fresh join

`joinRoom` has three outcomes, and callers must handle all three:

1. **Rejoin** — the id is already in `state.players`. Seat, role, and alive status are all
   preserved; `restorePlayer` clears the absent flag. Not subject to `maxPlayers`.
2. **Spectator** — game in progress, id unknown to it.
3. **Fresh member** — no game yet, and `maxPlayers` applies.

A room is destroyed only when `members` **and** `spectators` are both empty. Tearing it down while
spectators remain strands them in a room whose `sync` returns nothing.

`resetToLobby` (rematch) promotes spectators to full members, truncating at `maxPlayers`, and
keeps `config` so "same settings again" is one click.

## Host transfer

When the host leaves, `rooms.js` promotes `members[0]` and — this is the part that gets missed —
must also write `room.state.hostId`. The room-level and state-level host ids are two separate
fields; updating only the first leaves in-game host actions (`applyAction` checks
`playerId !== state.hostId`) still pointing at someone who has left, and the game cannot be advanced.
